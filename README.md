# lo-life

Lolita **上新助手**：看有什么新的、关注几个牌子、不懂的查知识库。跑在你自己机器上的本地优先 Web 应用（可安装为 PWA，手机同样能用）。

四个页面：**推荐**（最近上新，按偏好排序）· **偏好**（店家 / 风格 / 款式标签）· **知识**（问答/尺码/洗护）· **我的**（账号）。

知识检索与答案生成**不在这里实现**——直接复用 [lolita-rag](../lolita-rag) 的清洗、切分、BGE 向量、混合检索、五道闸门与答案校验。这个仓库只做三件事：

1. **用户状态**：账号、关注了哪些品牌、喜欢哪些店和风格（SQLite）
2. **前端**：原生 JS、零依赖、零 CDN 的 PWA
3. **服务层**：把知识问答转发给上游管线，不重写它

---

## 为什么这么分

|  | 上游 lolita-rag | 本仓库 |
|---|---|---|
| 职责 | 知识管线（与数据源无关） | 应用层（内容 + 用户状态 + 界面） |
| 语料 | 采集的微博 UGC（**仅本地私有**） | **自有整理**的知识库（可对外） |
| 索引 | `data/index/` | `data/kbindex/` |

两条硬纪律：

* **自有内容与微博语料永不混用。** 上游语料是他人 UGC，授权范围只到个人研究；而对外的页面必须只吃自有内容。管线是通用的，换数据源即可。
* **本服务不持有任何微博 Cookie。** 上游 `.env` 里有 `WEIBO_COOKIE`，这里构造上游 `Settings` 时显式传 `_env_file=None`，从根上不读它。

## 快速开始

```bash
# 0) 装依赖：本仓 + 上游检索管线（上游那份含 jieba / 向量库 / embedding 模型）
python -m pip install -r requirements.txt
python -m pip install -r <lolita-rag 路径>/requirements.txt

# 1) 配置（按需改 LOLITA_RAG_ROOT 为上游仓库真实路径）
copy .env.example .env

# 2) 生成 PWA 图标（一次即可）
python scripts/make_icons.py

# 3) 建知识库索引（首次约 6 秒，之后增量约 5 秒）
python scripts/build_kb_index.py

# 4) 起服务
python -m app.main            # http://127.0.0.1:8787
```

浏览器打开 `http://127.0.0.1:8787`。手机访问见下面「手机怎么用」。

**没有 `LLM_API_KEY` 也能完整跑通**：问答会自动退化为「原文摘录 + `[n]` 引用」，和上游同一套兜底逻辑。这样第一次出问题时，能立刻分清是**检索坏了**还是**生成坏了**。

### 检索默认只展示最相关的一条

`TOP_K` 默认 **1**。知识库的一条就是"一个主题写完整"的段落，多取几条通常只是同话题的邻居，展示出来是噪声。

但并列的多意图问句（「烫金和蕾丝怎么洗」）会在检索前拆成子问题，各自取一条再合并；合并上限 **5 条**，前端会在答案下方标出实际拆分结果。比较类问句（「JSK 和 OP 有什么区别」）保持整体检索——知识库里往往有一条专门写对比的条目，拆开反而会把这条打散。

这里有一个容易做错的地方：**收敛必须发生在检索层，不能只在前端隐藏**。答案里的 `[n]` 与返回条目一一对应，前端藏掉第 2 条之后，答案引用 `[2]` 就点不到任何东西，`verify` 的引用越界检查也会因为两边口径不一致而误判。

对非并列问句，`TOP_K` 仍然决定取几条；调大后界面会同时出现更多来源卡片，编号保持一致。

### `bridge.py` 的三条纪律

1. **不读上游 `.env`**（`_env_file=None`）——否则这个对外服务的进程里就握着一份账号会话。
2. **不调上游的 `ask()` / `retrieve()`**——它们会写 `queries.jsonl`，而那是上游唯一的「真实用户查询」信号源，工具层往里灌数据会污染它的拒答率统计。这里只拼装同样的三步：`search` → `Generator.answer` → `verify_and_degrade`。
3. **`verify_and_degrade` 一步都不能省**——它把「模型可能编造」变成「物理上不可能」（不达标就换成逐字摘录）。

## 上新怎么录

一条上新 = `content/newarrivals/` 下的一个 JSON，**不用重启**（每次请求现读）。复制 `_template.json` 改就行，字段说明在 [content/newarrivals/_README.md](content/newarrivals/_README.md)。

```json
{
  "id": "2026-10-baby-qiuri",
  "brand": "baby",
  "brand_name": "Baby",
  "series": "秋日私语",
  "release_date": "2026-10-29",
  "price_range": "295 - 880",
  "items": ["JSK", "SK", "KC"],
  "styles": ["甜系", "古典"],
  "image": "",
  "note": "全款预定，10 月中下旬发货",
  "source": "依据：品牌官方公告",
  "sample": false
}
```

**为什么默认手工维护**：上新信息来自品牌官方公告、店铺页面、官方社交账号，都是他人发布的内容。自动抓取再展示涉及转载授权和平台条款，而这个项目从第一天起就把"内容只用于自用、不二次公开发布"写进了原则。一周几条的录入量不大，换来的是数据干净、来源可查。

Baby 官网现在多了一条**草稿扫描**：只读官方 `products.json`，生成到 `content/_drafts/newarrivals/`，人工确认后才进正式内容：

```bash
python scripts/scan_baby.py --days 30            # dry-run
python scripts/scan_baby.py --days 30 --write    # 写草稿
python scripts/scan_baby.py --list               # 看草稿
python scripts/scan_baby.py --approve <id>       # 确认一条
```

自动只负责"发现 + 抄官方字段"，发售日、风格、款式仍需人看一眼；草稿目录和正式内容分开，`load_newarrivals()` 不会读到草稿。

### 单页入库：任意页面 → 草稿 → 人工确认

`scan_baby.py` 是 Baby 官网的**批量结构化扫描**；单条页面（AP 官网、淘宝另存页、临时公告）走 `ingest_newarrivals.py`：

```bash
python scripts/ingest_newarrivals.py --from-html 页面.html --brand ap --page-url 原始地址
python scripts/ingest_newarrivals.py --from-page https://… --brand ap
python scripts/ingest_newarrivals.py --retry data/ingest/drafts/xxx.json
python scripts/ingest_newarrivals.py --approve data/ingest/drafts/xxx.json
```

- 默认**只写 `data/ingest/`**（raw 快照 / 草稿 / rejected / runs.jsonl）；只有 `--approve` 会写 `content/newarrivals/`；
- 模型只负责抽字段，每个非空字段都要带**原文引文**；引文对不上就丢弃该字段，状态降为 `partial`；
- 没有 `LLM_API_KEY` 时跳过模型，结构化字段（图/链接/价格）照常保留，其余人工补；
- 模型调用失败写 `extract_failed` 草稿并保留 raw 快照，`--retry` 从同一份快照重跑，不重新抓页面；
- `partial` 草稿手工补全后可以审批；`extract_failed` 也可以先补字段再审批；`rejected`（重复 id / 非法 id）永远不能审批；
- 审批会二次校验必填字段、日期、风格词表和重名；已有条目要显式 `--overwrite`。

三条容易错的：

- **`release_date` 用发售日，不要用录入日。** 用录入日会让所有条目都"很新"，推荐页直接失去意义。
- **`brand` 和 `content/size/*.json` 的 `brand` 对齐。** 对齐之后，推荐页的「算尺码」按钮能直接跳到该品牌的尺码表——这是两个页面唯一真正的连接点。
- **`styles` 只能从固定词表里选。** 写「甜美」「甜」都不会匹配到偏好里的「甜系」，会被静默丢弃（`load_newarrivals` 只保留合法值）。
- **`sample: true` 会让页面顶部显示醒目提示。** 现在生效的条目已按官网数据替换；仍带 `sample: true` 的是占位/归档数据，别当真实上新。

### 排序为什么不"智能"

分数 = **新鲜度**（0~30）+ 每个偏好轴的匹配加分，全部可解释：

| 轴 | 每条加分 | 最多计几个 | 匹配字段 |
|---|---|---|---|
| 喜欢的店家 | +100 | 1 | `brand` |
| 喜欢的风格 | +40 | 2 | `styles`（集合求交） |
| 自定义标签 | +30 | 2 | 系列名 / 备注 / 品牌名 / 款式 / 风格（**子串**匹配） |
| 常穿的款式 | +25 | 2 | `items`（JSK / OP / SK…） |

刻意没做「猜你喜欢」：只有上新条目，没有点击和购买行为，任何"智能排序"都只能靠编。

> 这张表里的分值**只在服务端参与排序，界面上不显示**。卡片上给的是「你喜欢的店」「风格：甜系」这样的**文字说明**，不是数字。用户要知道的是"为什么这条排前面"，而不是一套内部打分。

## 搜上新：关键词、价格、尺码、链接

推荐页现在能"搜"，一张卡片上给齐**图片 / 价格 / 尺码 / 跳转链接**。四样东西的来源不同，分界必须说清：

| 卡片上的东西 | 从哪来 | 谁来算 |
|---|---|---|
| 图片 | 条目的 `image`（外链或 `/media/…`） | 原样展示，空则用品牌首字占位 |
| 价格 | 条目的 `price_range`（**字符串，不改成数字**） | `app/domain/price.py` 容错解析出区间 |
| 尺码 | `content/size/*.json` | `app/domain/size.py`（确定性查表） |
| 跳转链接 | 条目的 `link` | `app/domain/urls.py` 校验协议后才放行 |

**这四样一个都不进 RAG。** 知识库回答的是「JSK 和 OP 有什么差别」，不是「哪条上新符合我」。把上新塞进向量检索，会得到一个"每次搜出来不一样"的列表——而用户是在拿钱做决定。

### `GET /api/feed` 的四个新参数

```
q=秋日 JSK        关键词。空白分隔，**多个词是 AND**（不是 OR）
sort=score        可选 score / date / price_asc / price_desc
price_min / price_max   按解析出的区间过滤
```

三条刻意的口径：

- **搜索是过滤，不是加分。** 关键词命中的条目只决定"出现不出现"，不参与 `score`。否则用户搜「秋日」会看到一堆不含秋日的条目排在下面，他会认为搜索坏了。
- **价格解析只发生在读取侧。** `price_range` 保持字符串（"295 - 880"、"¥699 起"、"一件 480，整套 1100"都能解析），解析失败就置空、原样展示——**不因为价格写错就让整条上新消失**。
- **没标价格的条目不参与价格筛选。** 勾了"500 以下"却看到一条不知道多少钱的裙子，比漏掉它更让人恼火；空结果文案会说明这一点。
- **价格排序时没价格的排最后**，不冒充"最便宜"。

### 价格怎么显示

价格**单独一行、字号比正文大**，不在灰色的 `日期 · 几天前 · ¥价格` 里混着——那一行里
数字太多，会被当成"又一串数字"直接跳过，而价格是决定买不买的第一条信息。

- 有价格：`¥55,000`（accent 色、17px，四位以上自动加千分位）
- 没价格：`价格未标`（灰、12px）——**不写 ¥0**
- 文本里已经带货币标记（`41800 日元` / `USD` / `元`）就不再补 `¥`，避免 `¥41800 日元`

### 币种是条目上的一个字段，不靠品牌猜

```json
{ "price_range": "55000", "currency": "JPY" }
```

渲染成 `¥55,000 日元`。**CNY 不标**——`¥` 已经说明是人民币，每张国内卡片都挂一个「元」
是纯噪声；只有非 CNY 才追加那两个字。

为什么不把「日元」写进 `price_range`：写进去之后，价格筛选、排序、区间解析都得先把
那两个字剥掉，而且 `¥55000 日元` 读起来是重复的。分成两个字段，各自干一件事。

取图时如果条目还没写价格，**价格和币种会一起填**——币种从
`content/shops/<brand>.json` 的 `currency` 取。只写数字不写币种，等于把一个 55000
的日元价冒充成人民币。

### 官网价可以自动带进来

`app/domain/images.py` 从商品目录里一并抽价格：

- **HTML 列表页**（AP 这种）：价格不在 `<a>` 里，是页面上一段独立文本。按**位置区间**配——
  从这一条的标题开始、到下一件商品的第一个 `<a>` 之前，区间内第一个价格才是它的。
  这样既不会串到下一件，也不会抓运费/税/推荐位。
- **Shopify JSON**（Baby 这种）：`variants[0].price`，只取整数部分（`41800.00` → `41800`）。

裸数字（商品编号 `262J10`、尺码 `S M L`、年份 `2026`）**不算价格**。

写回时有一条限制：**只在条目 `price_range` 为空时才填**。手录的价格可能是代购价、
定金价，不该被官网原价悄悄顶掉。

### 尺码在列表里怎么显示

三档，各自分得清，谁也不冒充谁：

| 情况 | 卡片显示 | 状态 |
|---|---|---|
| 品牌有表，且条目的 `items` 命中表里的品类 | `JSK S/M/L/XL` + 版型（偏小/偏大） | 可选码 |
| 存过三围（登录后来自账号，未登录来自本机） | `JSK 你的码 M`（绿） / `最大码也不够`（红） | 算出来的码 |
| 没这个品牌的表 / 品类不在表里（KC、斗篷…） | 灰字「无尺码表」「品类未收录」 | 明确说没有 |

**`POST /api/feed/sizes`** 批量算码：传一批条目 id + 三围，每条返回 `ok / no_chart / no_category / need_measurements / item_level_only / unknown_id` 之一。批量场景**不允许因为一条没表就整个请求失败**——10 条里 8 条能算，用户要的是那 8 条。

### 身材数据：登录后存服务端，未登录只存本机

- **登录后**：围度存在服务端 `body_profile` 表（`GET/PUT/DELETE /api/profile/body`，三个方法都要求登录）。
- **未登录时**：只写 `localStorage` 的 `lo-life-measure`，算尺码本来就不需要账号。
- 两条路径共用同一份前端缓存：启动/登录后从服务端拉一次，把胸/腰/臀/肩镜像到 localStorage，尺码页与列表徽标因此立刻能用。在尺码页算完保存时，登录用户会同步回服务端——**部分更新**，只提交这次真的填了的围度，不会把「我的」页里的身高体重或别的围度清掉。

隐私边界：

- 身材是**单独一张表**，注销账号时随账号一起真删；导出备份会包含它（备份本来就是整库）。
- 身高体重只用于 BMI 提示，不参与选码；提示词只告诉模型「填过 / 没填」，不发送具体数值。
- **退出登录 / 删号会清掉本机缓存**，避免同一个浏览器上下一个登录的账号继承上一个人的围度。

「尺码助手」页仍有**看得见的「清除」按钮**，输入框会预填已记住的值——用户要知道它记住了什么、存在哪、怎么删。

### 出口链接必须过白名单

`link` / `image` 来自**手录 JSON**（也可能来自备份恢复、别人给的条目文件）。前端 `esc()` 只转义 HTML 实体，**不校验协议**——`javascript:alert(1)` 放进 `href` 照样执行。所以 `app/domain/urls.py` 在序列化出口只放行三种：`http(s)://`、站内 `/media/…`、空串；`data:`、`javascript:`、协议相对地址 `//evil.com`、带 `..` 的路径一律变空串（前端据此不渲染按钮）。前端再校验一次，两道都留着，成本几乎为零。

## 图片怎么来

**页面渲染不抓取。** 图片只有三个入口：你上传（`POST /api/media`）、界面上点「取图」、或命令行
脚本取一次再落到 `data/media/`。推荐页只读本地 JSON，不会因为某个站挂了而变慢或报错。

### 界面上点一下（推荐）

卡片上没图时有一个**「取图」**按钮：

- 品牌登记过 `page_url` → 点一下就开跑，不用输任何东西；
- 没登记 → 就地展开一个输入框，粘贴这一条的淘宝详情页地址（或店铺上新列表页）即可。

跑完卡片立刻出图，并且**顺手写上淘宝详情页链接**（从列表页里那层 `<a>` 抽出来，`spm` 全剥掉）。

后端是 `POST /api/images/fetch`，三条约束写死在实现里：

| 约束 | 为什么 |
|---|---|
| **只允许本机**（非回环地址 → 403） | 这个端点会把任意 URL 抓回来落盘，不该是"局域网里谁都能调"的接口 |
| **同一时刻只跑一次**（并发 → 429） | 并发写回同一个 JSON 会互相踩，也更容易触发风控 |
| **不做重试** | 失败就把原因（HTTP 403 / 登录墙 / 配不上系列）原样返回，让人换输入。自动重试会把握手变成撞门 |

它不在页面加载路径上：搜索、排序、渲染全都不碰它。

> **一个容易误判的环境问题**：这台机器的 Anaconda Python 里 `ssl.get_default_verify_paths()`
> 指向一个不存在的 `cert.pem`，于是所有 https 请求都报 `CERTIFICATE_VERIFY_FAILED`，
> 症状长得像"网站挂了"。`app/services/imagefetch.py` 显式用 certifi 的 bundle 建上下文，
> 并**保持 `CERT_REQUIRED`**——换 CA 包是为了能连上，不是为了关掉校验。

|---|---|---|
| `ap` | `angelicpretty.com` 新作列表 | HTML。列表页里**图和标题是两个指向同一商品的 `<a>`**，按地址归并 |

### 命令行批量

```bash
python scripts/fetch_images.py --brand ap                          # dry-run：只列候选
python scripts/fetch_images.py --brand ap --write                  # 真的下载并写回
python scripts/fetch_images.py --id 2026-10-ap-bainiao --from-html 白鸟笼.html --write
python scripts/fetch_images.py --id 2026-10-ap-bainiao --from-page https://…

```

| 入口 | 抓不抓 | 什么时候用 |
|---|---|---|
| `--from-html 页面.html` | **零请求** | 店铺页要登录、或抓不动时：浏览器里另存为 HTML，脚本只解析这个文件 |
| `--brand ap` | 抓一次 | `content/shops/ap.json` 里登记了 `page_url`（官网新品页 / 店铺上新页） |
| `--from-page URL` | 抓一次 | 某一条商品的详情页，精确到条 |

`--from-html` 那条最关键：**发请求的是你的浏览器，而且是你本人点的**。风控、登录墙、
防盗链全都不存在，因为脚本从头到尾没联网。淘宝店铺页大概率只能走这一条。

### 默认只看不改

不加 `--write` 时不下载、不改文件，只打印候选（带分数和「近旁文字」）。抓错图比没有图更糟：
用户会照着别人的裙子下单。

### 候选是怎么筛的

一个商品页有几十个 `<img>`：logo、导航图标、优惠券、推荐位、模特图、尺码表、1×1 埋点。
`app/domain/images.py` 只做一件事——**把 60 个降到 3 个**，剩下的交给你一眼判断：

- 扩展名：`.svg` / `.gif` 直接丢（都是图标和动图）；
- 文件名里的尺寸：`_800x800` 加分，`_120x120` 减分；
- 文件名里的坏词：`icon / logo / sprite / qrcode / placeholder …`；
- **刻意不看路径**：`/item/` 在有些站是页面路由，拿它判断只会误杀。

### 列表页怎么把图和条目对上

`--brand` 抓的是品牌的新品**列表**页，一页几十个商品。配对只靠一条规则：
**图片前后 600 字里出现了系列名**。比较前先去掉空格（`秋日 私语` 能对上 `秋日私语`），
但**不做模糊匹配、不做同义词**——配不上就报"没配上"，让你用 `--pick` 或换成详情页。
宁可留空，也不给错图。

### 跳转到底去哪（三级，文案各不相同）

| 有什么 | 按钮 | 目标 |
|---|---|---|
| 条目 `link` 或列表页里抽到的 `item id` | **去商品** | `item.taobao.com/item.htm?id=…` / `detail.tmall.com/item.htm?id=…` |
| 没条目链接，但 `content/shops` 里有 `shop_url` | **去店铺** | 店铺首页 |
| 都没有 | **淘宝搜** | `s.taobao.com/search?q=品牌 系列` |

详情页地址只保留 `id`，`spm` / `scm` / `ali_trackid` 全部丢掉——那些是推广追踪参数，
换一次点法就变一次，存进 JSON 等于存了个会过期的指纹。

**第三级不是详情页**，所以按钮写「淘宝搜」而不是「去商品」。详情页地址拼不出来，
也不该拼：它必须来自真实数据（`link` 字段，或列表页里抽到的 `item id`）。

`--from-page` / `--brand` 抓店铺上新列表页时，脚本会把**每张商品图外面那层指向详情页的
`<a>`** 一起解开，图和详情页链接一次拿齐：

```
 →2. https://detail.tmall.com/item.htm?id=700000002
      …_800x800.jpg（近旁：AP 白鸟笼 立领无袖 JSK）
  → 详情页：https://detail.tmall.com/item.htm?id=700000002
  → 已写入 2026-10-ap-bainiao.json：image=/media/4ba6….png，link=https://detail.tmall.com/item.htm?id=700000002
```

### 会被拒绝的地址

`taobao.com` / `tmall.com` 的 robots.txt 是 `Disallow: /*?*`，**带查询参数**的地址一律不抓。
脚本遇到直接退出并说明原因，**没有跳过开关**。无参数的店铺页不在禁止范围内。

### 三个副作用，先知道

- 脚本写回时用 `indent=2` 重排整个 JSON，所以**短数组会从一行展开成多行**，
  git diff 会比你真正改的那一行大（JSON 不能局部替换，这是必然代价）。
- `--brand` 需要 `content/shops/<brand>.json` 里有 `page_url`，否则无从下手。
- 店铺页抓到的是列表时，没登记 `page_url` 的品牌会直接报错，不会静默跳过。

## 专属推荐：偏好 tag 怎么变成"你该看哪几条"

**推荐页就是这一页。** 登录且有偏好时，「推荐」不再是一块推荐 + 下面一整个全部列表，
而是**只有一份列表**：命中你偏好的条目。右下角「看全部上新」切回全量（搜索、筛选、排序在那边）。

```
Lovely Princessジャンパースカート
¥55,000 日元
2026-10-30 · 3 天前
[喜欢的店] [口味]        ← 推荐原因（原有的 reasons）
相关知识：JSK 和 OP 有什么区别
[喜欢这家店] [算尺码] [去商品]
```

两条回退规则，都是为了不留空白页：

- **没登录** → 全部上新（匿名也有东西看）；
- **有登录但推荐为空**（没设偏好、或没有一条命中）→ 自动退回全部。
  "你没有偏好"和"你没有符合偏好的上新"是两个状态，只有后者才该空。

### 十条，按上新日期倒序

`GET /api/recommendations?limit=10&sort=date`（`sort` 默认就是 `date`）。

**筛选靠偏好，顺序靠日期。** 这是刻意的：用户打开推荐页想先看到"最近上了什么"，
而不是"算法觉得我多喜欢"。要看加权排序就把 `sort` 换成 `score`（店家 +100 / 风格 +40
/ 类别 +25，同 `feed()`）。

先取 200 条再筛、再截断——反过来先截断会把"命中偏好但排在 21 名之后"的条目直接丢掉，
而它们恰恰可能是用户要看的。

`GET /api/recommendations`（需登录）返回命中的条目、按轴分好的组，以及**卡片需要的全部数据**
（`size_charts` / `shops` / `has_sample_data`）。自带这些不是偷懒：推荐页现在是主列表，
如果尺码表和店铺表只由 `/api/feed` 返回，"只看推荐"模式下卡片上的尺码徽标和「取图」
按钮会因为缺数据而悄悄消失。

```
count = 3   kb_ready = True   size_charts = 3   shops = 3
  1. Dark Night Sweets柄 ジャンパースカートII  ¥41,800 日元  [图]
     命中 喜欢的店家:baby · 喜欢的风格:甜系   相关知识 JSK 和 OP 有什么区别
  2. Dark Night Sweets柄 ワンピース           ¥57,800 日元  [图]
     命中 喜欢的店家:baby                   相关知识 JSK 和 OP 有什么区别
  3. Lovely Princessジャンパースカート          ¥55,000 日元  [图]
     命中 喜欢的风格:甜系                   相关知识 JSK 和 OP 有什么区别
```

### 三段，各干各的

| 段 | 做什么 | 在哪 |
|---|---|---|
| **召回** | 偏好 tag 与条目求交 | `app/domain/recommend.py`（纯函数） |
| **排序** | 复用 `feed()` 的加权：店家 +100 / 风格 +40 / 类别 +25 | `app/domain/newarrivals.py` |
| **背景** | 拿条目的**品类**（JSK / OP）查知识库，命中就挂一条标题 | `app/bridge.py` 的 `search_kb()` |

没命中任何偏好 tag 的条目**不进推荐**——"专属"不能靠把全量塞进来充数。

### 偏好 tag 为什么不查 RAG

因为查不到。用真实偏好 tag 实测（`top_k=3`）：

```
'ap' -> 0 条    'baby' -> 0 条    'huayuzhenzhuxia' -> 0 条    '甜系' -> 0 条
对照：
'JSK' -> term-jsk-op (1.181)   '裙撑' -> guide-chengqun (1.272)   '烫金' -> care-jinshu (1.071)
```

知识库里是术语、尺码、洗护、指南，**没有商品，也没有风格/店家标签**。所以：

* 拿 tag 去 RAG，命中 0 条 → 推荐为空；
* 就算硬塞给它，那也是"让一个没见过商品的语料库来决定买哪条裙子"。

RAG 在这里唯一站得住的位置是**解释背景**：你偏好 JSK，卡片下面挂一条「JSK 和 OP 有什么区别」。
它不参与召回，也不参与排序。

### 这个功能不需要 tool

不需要 function calling。需要的是一条**确定性链路**：

```
登录态 → 读偏好（SQLite）→ 与条目求交（纯函数）→ 加权排序 → 挂一条知识命中
```

全程没有一步需要模型"决定调什么"。把模型放在这条链路上会得到：同一批数据两次刷新
顺序不同、失败时无法解释、以及一个额外的延迟来源。**tool 是"模型需要访问外部能力"时的
解法**；这里四步都在本进程里，直接调用就行。

知识库没建、或检索抛错时，这个接口**照样 200**，只是 `knowledge` 为 `null`、`kb_ready=false`——
推荐是确定性计算，不该被另一个子系统的状态拖下水。

## 助手：单 agent + 并行取证

助手只有**一个** planner 循环（`app/agent/loop.py`），没有多 agent 对话。理由不复杂：

* 工具是顺序选择的，子任务之间没有需要协商的依赖；
* 步数上限、连续空结果即停、引用越界降级这些护栏都在一个循环里，多一个 agent 就要复制一套，失败归因也更难；
* 一次问答的模型调用次数直接等于成本和延迟。

唯一的"专家"是 `item_profile`：给它一个系列名，它把**条目事实、合身判断、商品/店铺链接、相关术语**四路取证并发跑完（固定小 DAG，`ThreadPoolExecutor`），合并成一份档案交给 planner。它刻意不是第二个对话 agent——没有独立提示词、没有循环、没有重试；知识库没建时只是少一路证据，不影响其余结论。这样 planner 一次调用就能回答"这件我穿得上吗、多少钱、哪儿买"，而不是连查三次。

## 账号与偏好

浏览（推荐、知识、尺码、洗护）**不需要登录**；保存偏好需要——偏好是跟着账号走的，做成多账号才有意义，否则"登录"只是装饰。

| 接口 | 说明 |
|---|---|
| `POST /api/auth/register` | 注册，返回令牌 |
| `POST /api/auth/login` | 登录，返回新令牌 |
| `POST /api/auth/logout` | 吊销当前令牌 |
| `GET /api/auth/me` | 未登录返回 `200 + user: null`（前端少一个分支） |
| `DELETE /api/auth/me` | 注销账号，连同会话/偏好一起删（**真删**，同名可重新注册） |
| `GET /api/preferences/options` | 轴的元数据 + 每个轴的可选标签（**不需要登录**，前端要先能渲染） |
| `GET/PUT /api/preferences` | 读/写偏好（写操作需要登录） |
| `GET /api/feed` | 推荐（匿名可用，带上令牌就按偏好排序）。支持 `q` / `sort` / `price_min` / `price_max`，响应里带 `size_charts` |
| `POST /api/feed/sizes` | 批量算码：一批条目 id + 三围 → 每条的 `ok / no_chart / no_category / need_measurements / item_level_only / unknown_id` |
| `GET/PUT/DELETE /api/profile/body` | 身材参数，**三个方法都要登录**；未登录时前端只写本机缓存 |
| `GET /api/export` | 实例级备份 zip，**必须登录** |
| `GET /api/chat/runs` | 最近的问答轨迹，**必须登录**（轨迹里是原始问题与回答） |

### 偏好是多轴的标签

以前有「关注品牌」和「偏好的店」两套开关，都表示"我喜欢这个牌子"——用户分不清该点哪个，排序里还会同类信号叠加。现在**只有一套偏好，由多个轴组成**：

```
喜欢的店家  [Baby] [AP] [花与珍珠匣]
喜欢的风格  [甜系] [古典] [哥特] [蒸汽朋克] [和风] …
自定义标签  [齿轮 ×] [鸟笼 ×]          ← 自由输入，每个可单独删
常穿的款式  [JSK] [KC] [OP] [SK]
```

标签上**只显示名字**，不显示"有几条能匹配"——标签是偏好，不是数据统计。接口仍然返回这个条数（`options[*].count`），调试和将来做热度排序时用得上。

**加一个新轴（比如价位带）不用改代码路径**：在 `app/domain/axes.py` 的 `AXES` 里加一条 `Axis`（匹配字段 + 权重 + 最多计几个 + 原因写法），排序、校验、接口选项、前端标签组全部自动跟上。因为：

* 排序是**遍历轴表**算分，没有"如果有风格偏好就…"这类分支；
* 前端的标签组件由 `/api/preferences/options` 返回的**元数据**驱动（含 `allow_custom`），不为几个维度写死几段 UI；
* 数据层 `preferences(user_id, axis, values_json)` 一行一个轴，加轴不改表结构。

### 自定义标签：唯一的自由输入

其余三个轴的值必须**先在内容里存在**，所以只能从列表里挑。自定义标签是例外——它不看"值是否存在"，而是按**子串**去匹配条目的系列名 / 备注 / 品牌名 / 款式 / 风格：

```
输入「齿轮」→ 命中系列名「缎带与齿轮」→ +30，卡片显示「关键词：齿轮」
输入「可拆」→ 命中另一条的备注「附可拆缎带」→ +30
```

自由输入有两个护栏，缺一不可：

1. **边界**：单个标签 ≤ 20 字、每个轴 ≤ 20 个（服务端 `axes.CUSTOM_MAX_LEN` / `CUSTOM_MAX_ITEMS`，前端保持一致）。不设上限，存储和排序会被无限增长的关键词拖垮。
2. **命中回报**：`GET/PUT /api/preferences` 返回 `match_report`，列出哪些标签在当前内容里匹配不到；界面会显示黄条「这些自定义标签在当前内容里没有匹配到：量子计算」。**没有这个回报，用户写了个永不命中的词只会以为功能坏了**——这正是我一开始反对自由输入的理由，现在它被明确告知了。

> 子串匹配刻意用 `in` 而不是正则：用户输入直接进正则有灾难性回溯风险，而这里不需要任何模式能力。代价是它很朴素——`缎` 会命中 `缎带`，也没有同义词与分词。

### 部分更新语义

`PUT /api/preferences` **只替换传进来的轴**，没传的保持不变。这样前端可以一块一块保存（改店家不动风格），也避免"少传一个字段就清空其他偏好"——那是最容易让人暴怒的一类 bug。传空数组表示**清空该轴**。

### 安全上做了什么、没做什么

**做了**：密码用 `hashlib.scrypt` + 每用户独立盐；登录态是随机令牌存库（**能立刻吊销**，比 JWT 的"无状态"重要）；用户名不存在时也跑一次哈希，避免用响应时间探测账号是否存在；登录失败统一返回「用户名或密码不对」；**备份导出与问答轨迹两个敏感读取接口都要求登录**——前者是整库（含所有账号密码哈希），后者是原始问答文本，匿名开放等于把它们交给同网段的任何设备。

**没做**：找回密码、邮箱验证、登录失败锁定、多因素。代价必须清楚——**忘了密码等于这个账号的数据拿不回来**；明文 HTTP 下令牌可被同网段嗅探（局域网用请走 Tailscale）。

### 升级迁移：旧数据不会丢

表结构变过三次，每次都有对应迁移——偏好是用户唯一的"设置"，丢了就找不回来：

| 起点 | 处理 |
|---|---|
| M1 的 `items` / `outfits` / `wishlist` | 直接丢弃（当时确认过是空表） |
| M2 的 `follows`（**没有** `user_id`） | 改名为 `follows_orphan` 保留；**第一个注册的账号**把它并进自己的「喜欢的店家」轴，然后删旧表 |
| M3 的 `follows`（有 `user_id`）+ `preferences(shops, styles)` | 合并进新的轴模型，然后删旧表 |

顺序是刻意的：**先读进内存 → 再删表 → 建新表 → 最后写回**。反过来会在 Windows 上撞到 WAL 句柄，也会在出错时丢掉不可恢复的数据。

迁移会**保留用户原来选的顺序**（用有序字典而不是 set）——偏好本身无序，但升级时无故重排成字典序，会让人以为"我的设置被改了"。

> `orphan_shops > 0` 时冒烟脚本会拒绝注册临时账号：临时账号会把待认领的店家认领走，再随注销一起删掉。这个保护必须有——冒烟脚本不该有破坏真实数据的能力。

## 偏好页

标签组件由服务端元数据驱动（`app/static/app.js` 的 `createTagGroup`）：一个轴一组，每组显示标签 + 匹配条数 + 已选数 + 清空按钮。**服务端加新轴时前端不用改代码。**

* 选项**来自内容**：店家与款式从 `content/newarrivals/` 反推，风格是固定词表——不另建品牌表，避免两处维护同一份事实；
* 保存是部分更新语义（传空数组即清空该轴）；
* 保存后推荐页排序立刻变化，所以前端必须**重渲染整个列表**，不能只改按钮文字；
* 未登录时直接引导去登录，而不是渲染一堆点了才 401 的标签；
* 未知轴 / 未知选项一律 **400**：脏值会让排序永远匹配不上，而且极难排查。

## 知识库怎么写

`content/kb/*.md`，一条一个文件：

```
id: term-jsk-op
title: JSK 和 OP 有什么区别
category: 术语
tags: 版型,术语
---
正文第一段……

正文第二段……
```

四条规矩，都是被上游清洗规则或向量库逼出来的：

1. **写成纯文本，不要 Markdown 语法。** 上游的 `clean_text` 是为微博设计的，会吃掉 `#` 和空行，`## 标题`、`**加粗**` 只会留下噪声。
2. **`id` 必须唯一。** 上游的 `chunk_id` 是 `post_id#序号`，id 撞了会在向量库里互相覆盖**而且不报错**——所以入库时直接崩掉。
3. **每条正文要够长**（≥ 18 字，上游 `chunk_min_len`）。太短的条目会被静默丢弃，`ingest_kb.py` 会把被跳过的条目打出来。
4. **标题与正文合计不要超过 400 字。** 上游按 400 字切块；超了会被拆成多个片段，而默认 `TOP_K=1` 只会取到其中一块。要写更长，按主题拆成多条。

`title` 会被并进正文——否则「JSK」这类关键词 BM25 打不到。

改完知识库：

```bash
python scripts/build_kb_index.py --notify   # 增量建索引，并通知运行中的服务重载
```

`--notify` 很重要：服务是**启动时装载一次**索引的，不通知它就一直在用旧的，症状是「明明建了索引却搜不到新条目」。

## 尺码与洗护：为什么不走 RAG

这两个是**确定性**问题，塞进检索会得到一个"每次答得一样才怪"的助手——而用户是拿着钱在店里问尺码、或者在洗衣机前面问能不能机洗，错一次就丢信任。所以它们单独成层（`app/domain/`），**每次请求现读 JSON**，改完立刻生效。

### 尺码：`POST /api/size/recommend`

```
{brand, category, bust?, waist?, hip?, shoulder?}   →   {recommended, confidence, evaluated[], advice[], warnings[]}
```

三个建模点：

| 概念 | 为什么必须有 |
|---|---|
| **富余量 ease** | 成衣必须比身体松。直接拿胸围 84 比成衣 84 选码，会稳定选小一码。默认 胸/臀 4cm、腰 2cm、肩 0 |
| **版型偏移 fit** | 标「偏小」的牌子同标 M 实际更紧。`偏小` 抬 2cm、`偏大` 降 2cm |
| **不给身高体重** | 没有体型模型时，仅凭身高体重推不出胸腰围。硬给一个数字就是伪精确，所以接口只收真实尺寸 |

加一个品牌不用改代码：按 `content/size/_README.md` 丢一个 JSON 进去就行。

> 品牌表默认 `verified: false`。没核对过的表，卡片上只显示灰字「尺码表未核对」，
> **不会把占位数字当事实印出来**——「偏小」直接决定选大一码还是小一码，猜错就是买错。

`没这个牌子` 返回 **404** 而不是 500，也不套用别家的表。

### 真实数据长什么样：商品级，不是品牌级

把两家官网打开就会发现一件事——**它们根本不按 S/M/L 给尺寸**：

```
AP   ：・着丈:約89㎝  ・バスト:約91～101㎝  ・ウエスト切替位置:約74～86㎝
Baby ：サイズ 着丈：約99～104cm バスト：約90～99cm ウエスト：約74～85cm
```

这是一个**弹性区间**（抽褶、可调肩带），不是"某个码多宽"。硬拆成 `sizes: {S:{}, M:{}}`
只能靠编，而编出来的码数会让用户按一个不存在的 M 码下单。

所以尺寸存在**条目上**（`"size": {"kind":"free","label":"F","bust":[91,101],...}`），
`app/domain/garment.py` 从商品页正文解析，`size.judge_ranges()` 只给三种判断：

| 判断 | 依据 |
|---|---|
| `fits` | 身体 + 放量 落在区间内 |
| `loose` | 低于区间下限超过 8cm（靠系带能收，但收太多会跑形） |
| `too_small` | 超过区间上限，报出差几厘米 |

**不产出 S/M/L。** 区间型衣服报一个码数就是伪精确。卡片的徽标直接显示事实：
`F 胸91–101 腰74–86 长89`，鼠标悬停能看到来源（哪个官网页面、哪天取的）。

取数由 `scripts/fetch_sizes.py` 负责（AP 详情页 / Baby Shopify `.js` 各一条路径），
默认 dry-run，`--write` 才写回；原文照抄进 `size.source`，可回溯：

```bash
python scripts/fetch_sizes.py --brand ap
python scripts/fetch_sizes.py --brand baby --write
python scripts/fetch_sizes.py --id <id> --from-html 页面.html --write   # 淘宝/登录墙
```

**AP / Baby 的 `content/size/<brand>.json` 是 `kind: "item_level"`**：官方不提供品牌级
S/M/L 表，`categories` 为空。硬编一份品牌表只能靠猜，所以品牌级表只给真正按官方分码
录入的品牌；AP/Baby 的合身判断必须走具体商品的 `size`（`check_fit`）。

### 洗护：`POST /api/care/advice`

```
{materials[], crafts[], notes[]}   →   {machine_washable, headline, advice[], refs[], matched[]}
```

规则在 `content/care/rules.json`，一条规则只管一件事，用标签组匹配（**每组都要命中**才生效）。所以「蕾丝 + 烫金」会同时命中"蕾丝要装洗衣袋"和"烫金禁止机洗"——禁止项一票否决，但另一条的建议不会被吞掉。

没有匹配到规则时 `known: false`，直接说"以洗标为准"，**不套用最接近的一条**。

## 手机怎么用

PWA 的核心前提是 **HTTPS**：Service Worker 只在安全上下文里注册。用局域网地址 `http://192.168.x.x:8787` 访问时，**能看能用，但装不上、也没有离线**。

推荐 Tailscale（免费、真证书、免备案、不用公网 IP）：

```bash
# 1) 机器与手机都装 Tailscale 并登录同一账户
# 2) .env 里把 BIND_HOST 改成 0.0.0.0
# 3) 起服务，然后把本地端口代理成 HTTPS
python -m app.main
tailscale serve https / http://localhost:8787
```

手机用 `https://<机器名>.<tailnet>.ts.net/` 打开：

| 平台 | 安装方式 |
|---|---|
| Android Chrome | 菜单 → 添加到主屏幕（有安装提示） |
| iOS Safari | 分享 → 添加到主屏幕（16.4+ 才有推送） |

**微信里打开拿不到 PWA 体验**，要引导「右上角 → 在浏览器中打开」。

## 数据与备份

用户状态只有一份：**关注列表**（`data/app.db`）。内容全在 `content/` 里，本来就在 git 中。

* 界面：「我的」→「导出备份 zip」（未登录时不显示按钮）
* 接口：`GET /api/export`，**必须登录**

备份包是**实例级**的：里面有整库 `app.db`（所有账号的密码哈希、身材数据）与全部照片，
所以它不能是匿名接口。前端导出也要用 `fetch` 带 `Authorization` 头再走 blob 下载，
不能直接 `location.href` ——那样发不出 Bearer 头。

zip 里是 `app.db`（用 SQLite 的 `backup()` 复制，不是直接拷文件——库开着 WAL，直接拷可能拿到缺最新事务的半成品）、`media/`、`content/`（上新 + 知识库 + 尺码表 + 洗护规则）、`MANIFEST.json`。

恢复：把 `app.db` 与 `media/` 放回 `data/`，`content/` 放回项目根。

## 测试

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q            # 462 项：认证 / 偏好轴 / 上新 / 搜索排序 / 推荐 / 价格 / 取图 / 尺码 / 洗护 / 草稿 / agent / 数据层 / 接口
python scripts/smoke.py        # 63 项端到端，需要服务在跑
```

* `pytest` 用 `tests/.data` 作为数据目录（`tests/conftest.py` 在导入前设 `DATA_DIR`），**绝不碰真实 `data/`**。
* `smoke.py` 会注册一个临时账号（`smoke-xxxx`）、用完**注销**，连带它的关注与偏好一起消失；如果本机有 `orphan_follows`（升级前待认领的旧关注），它会跳过账号部分，避免把旧关注认领后删掉。
* 「知识库外的问题必须返回 `count=0`」是断言项，不是失败——拒答是设计内的行为。
* **API 测试不断言依赖"今天"的数字**：新鲜度随日期变，写死"7 天内必须有 N 条"过两周就红。时间逻辑在 `test_newarrivals.py` 里注入 `today` 测。

> 在受限文件沙箱里跑 pytest 时，加 `-p no:cacheprovider`：pytest 建缓存目录会被拒（`WinError 5`），只是警告，不影响结果。

## 已知粗糙处

| 问题 | 说明 |
|---|---|
| 拒答文案带「语料」二字 | 用的是上游 `NO_CONTEXT_REPLY`（"请换一种问法，或先补充语料后重建索引"）。对终端用户应该说「知识库」 |
| 上新主要靠手工录入 | Baby 已有 `scan_baby.py` 生成官方草稿，但仍需人工确认；其他品牌仍是手工录入 |
| 推荐只有三个轴 | 没有点击行为，做不出个性化。轴是可扩展的（加一条 `Axis` 即可），但"更准"得先有埋点 |
| 标签组不支持搜索 | 店家只有几个时没问题；到几十个就需要搜索或分组 |
| 自定义标签匹配很朴素 | 纯子串：`缎` 会命中 `缎带`，没有同义词、分词、大小写以外的一切归一化 |
| 搜索不做错字/拼音容错 | 搜「秋日」不会命中「秋天」。条目量小的时候可以忍；上千条就该上 SQLite FTS 而不是硬堆正则 |
| 价格筛选只有接口没有 UI | `price_min` / `price_max` 后端已支持并有测试，界面上只放了排序 chip。要加滑块时不用改后端 |
| 尺码只认 `items` 里表内有的品类 | 条目写 `KC`、表里只有 JSK/OP/SK 时显示「品类未收录」——不拿裙子的表算发饰的码 |
| 未登录时三围只在这台浏览器 | 登录后会同步到账号；不登录换设备/清缓存仍要重填 |
| 取图脚本会重排 JSON | 用 `indent=2` 整文件重写，短数组从一行展开成多行，git diff 比实际改动大 |
| 淘宝店铺页基本抓不动 | 登录墙 + 风控。脚本会明说失败原因；正确的走法是 `--from-html`（浏览器另存页面） |
| 列表页配对只认系列名 | 系列名多了括号/英文缩写就配不上。宁可留空也不猜——用 `--pick N` 手动指定 |
| 品牌级尺码表只有测试数据 | AP/Baby 已接官方商品级实测尺寸（`kind: item_level`），但品牌级 S/M/L 表仍需按官方表录入；没有官方来源的品牌不要编数字 |
| **没有找回密码** | 忘了密码等于这个账号的关注和偏好拿不回来。请存进密码管理器；也可以注册新账号重来 |
| **没有登录失败限速** | 本地单机场景可以接受；一旦暴露到公网必须先加 |
| 明文 HTTP 下令牌可嗅探 | 局域网/公网访问请走 Tailscale（加密隧道），不要裸奔 |
| 洗护规则偏少 | 目前 13 条。长尾组合会走 `known: false` |
| 无内容安全 | 自用/小范围可以；要公开就必须接内容安全审核 |

## 与上游的关系

本仓库通过 `sys.path` 导入 `lolita-rag` 的 `src` 包，**不复制它的代码**：那些阈值（`MIN_VECTOR_SCORE=0.44`、`DISTINCTIVE_DF_RATIO=0.10` 等）都是在真实数据上标定出来的，复制一份就等于把标定依据一起丢掉。

上游更新后这里自动生效；唯一需要跟着改的是它那两个公开接口的形状：`load_retriever()` 与 `verify_and_degrade()`。
